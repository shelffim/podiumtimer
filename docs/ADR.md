# Architecture Decision Records

## 철학
프로토타입 수준의 MVP다. 핵심 가치("계획 대비 몇 초 앞/뒤"가 발표자의 행동을 바꾸는가)를 검증하는 데 필요한 만큼만 만든다. 실서비스 수준의 견고함보다 작동하는 가장 단순한 구현을 고르고, 실서비스 전에 보강할 것은 PRD의 체크리스트로 미룬다. 외부 의존성과 언어·접근 방식의 가짓수를 최소로 한다.

---

### ADR-001: Next.js App Router + Vercel
**결정**: Next.js(App Router, TypeScript strict) + Tailwind CSS로 만들고 Vercel에 배포한다. 함수 리전은 서울.
**이유**: 화면·서버 액션·API 라우트를 한 저장소에서 처리한다. Harness의 TDD 가드와 훅이 Next.js 구조를 전제로 한다. Vercel은 CLI로 배포를 자동화할 수 있다.
**트레이드오프**: Vercel Hobby는 비상업 전용이라 실결제를 열 때 Pro로 바꿔야 한다. 서버 함수의 콜드 스타트로 참여자 화면 반영이 최대 1초쯤 늦을 수 있다 (시간 값은 이벤트 시각 기준이라 정확도는 그대로).

### ADR-002: Supabase 하나로 인증·DB·실시간
**결정**: Supabase Auth(Google), Postgres, Realtime(Broadcast + Presence)을 쓴다.
**이유**: 서비스 하나로 로그인, 저장, 실시간 동기화, 접속자 표시를 해결한다. 무료 티어로 시작할 수 있고 서울 리전이 있다.
**트레이드오프**: 무료 프로젝트는 1주 비활성 시 일시정지되고 Realtime 동시 연결이 약 200개다. 실서비스 전 Pro 전환이 필요하다.

### ADR-003: 세션 = 이벤트 기록, 화면 상태는 각자 계산
**결정**: 세션에는 `start`·`next`·`undo`·`pause`·`resume`·`end` 이벤트와 시작 시점의 계획 스냅샷만 저장한다. 화면 상태는 `computePace(계획, 이벤트, 지금 시각)`으로 계산하고, 매초 상태를 보내지 않는다.
**이유**: 취소, 일시정지, 늦게 들어온 참여자, 재접속, 리포트를 같은 순수 함수 하나로 처리한다. 메시지가 거의 없어 실시간 비용이 낮고, 지연이 있어도 시간 값이 정확하다.
**트레이드오프**: 모든 화면이 같은 엔진 코드를 공유해야 하고, 서버 시각 보정이 필요하다.

### ADR-004: DB 함수·트랜잭션 없이 supabase-js 조건부 업데이트
**결정**: 로직은 전부 TypeScript에 두고 DB 접근은 supabase-js 하나로 한다. RPC, 트랜잭션, 직접 DB 연결은 쓰지 않는다. 동시성은 한 번의 조건부 업데이트(`last_seq = 기대값`, `active_session_id is null`)와 유니크 제약(`polar_order_id`, 룸당 진행 중 세션 하나)으로 막는다.
**이유**: 한 언어·한 접근 방식으로 끝나고, TDD 가드가 모든 로직에 적용된다. 연결 풀 설정이 필요 없다.
**트레이드오프**: 여러 쓰기를 원자적으로 묶지 못한다. 룸 동시 생성으로 무료 한도를 1개 넘는 경우, 동시 웹훅으로 만료일이 잠깐 어긋나는 경우는 감수하거나 다음 계산에서 복구한다.

### ADR-005: 공개 Broadcast는 변경 힌트, 상태는 서버에서 다시 읽기
**결정**: 채널 `room:{shareToken}`은 공개 채널이다. 서버는 저장 후 `changed {sessionId, seq}`만 보내고, 화면은 이를 계기로 서버에서 상태를 다시 읽는다. 10초 주기와 화면 복귀 때도 다시 읽고, 조회는 한 번에 하나만 보낸다.
**이유**: 참여자 인증 없이도 누가 가짜 신호를 보내 화면을 조작할 수 없다. Broadcast가 실패하거나 신호를 놓쳐도 재조회로 복구된다.
**트레이드오프**: 신호마다 조회 요청이 생긴다 (룸당 최대 10명이라 부담이 작음).

### ADR-006: 참여자는 비로그인, 인원 한도는 화면에서 검사
**결정**: 참여자는 닉네임만 입력한다. 동시 접속 한도는 Presence 인원 수로 화면에서 검사하고, 서버에서 강제하지 않는다.
**이유**: 교실에서 학생이 QR만 찍고 바로 들어오게 한다. 익명 계정·좌석 테이블·하트비트가 필요 없다.
**트레이드오프**: 개발 도구로 한도를 우회할 수 있다. 실결제 전 서버 강제로 바꾼다.

### ADR-007: 링크 재발급 = 채널 교체 (CAPTCHA·내보내기 없음)
**결정**: 장난·유출 대응은 링크 다시 만들기 하나다. 채널 이름이 토큰이므로 링크를 바꾸면 기존 참여자는 모두 끊긴다.
**이유**: Zoom처럼 간단하게 대응한다. 개별 내보내기, 입장 횟수 제한, CAPTCHA를 만들지 않아도 된다.
**트레이드오프**: 한 명만 골라 내보낼 수 없다. 링크를 바꾸면 정상 참여자도 다시 들어와야 한다.

### ADR-008: 결제는 Polar 30일권 하나 (sandbox)
**결정**: 자동 갱신 없는 30일 이용권 하나만 판다. Polar(판매 대행)를 쓰고, MVP는 sandbox에서 전체 흐름까지 만든다. 다시 사면 만료일에 30일을 더한다.
**이유**: 한국 개인 판매자도 정산받을 수 있고 세금·환불 처리를 Polar가 맡는다. 구독이 없으니 갱신·해지·겹침 규칙이 필요 없다. 주 고객(교사, 행사 운영자)은 필요할 때만 사는 이용권이 맞다.
**트레이드오프**: 연간 구독 고객을 받지 못한다. Polar 수수료가 PG 직접 계약보다 높다.

### ADR-009: 환불되면 그 이용권은 무효 (부분 환불 포함)
**결정**: `order.refunded`가 오면 그 주문의 이용권을 기간 계산에서 뺀다. 부분 환불도 같다. 만료일은 웹훅마다, 결제 완료·계정 화면을 볼 때마다 전체 구매 기록으로 다시 계산한다.
**이유**: 금액·통화·비율 계산이 필요 없다. 같은 웹훅이 다시 오거나 순서가 바뀌어도 결과가 같다.
**트레이드오프**: 부분 환불이 사용자에게 불리하게 작동한다. 운영자는 전액 환불만 쓰는 것을 원칙으로 한다.

### ADR-010: mock/live 어댑터와 mock 선배포
**결정**: 화면은 `src/services/api` 인터페이스만 부르고, 구현은 mock(localStorage·BroadcastChannel·가짜 로그인·가짜 결제)과 live(서버 액션·Supabase·Polar) 두 개다. `NEXT_PUBLIC_DATA_MODE`로 고르고 기본값은 mock이다. mock 상태로 먼저 배포한다.
**이유**: 외부 계정 없이 화면과 핵심 로직을 먼저 만들고 배포한다. 1차 배포로 운영 주소가 정해져야 Google 로그인과 Polar 웹훅을 설정할 수 있다. 컴포넌트 테스트도 mock 어댑터로 돌린다.
**트레이드오프**: 저장·전송 구현이 두 벌이다. mock에서는 서버의 조건부 업데이트·웹훅 동작을 확인할 수 없다.

### ADR-011: Vercel CLI·Supabase CLI로 자동 배포와 DB 반영
**결정**: `npm run deploy`(Vercel CLI)와 `npm run db:push`(Supabase CLI)로 배포와 마이그레이션 반영을 자동화한다. 두 명령은 해당 step에서만 실행한다. 마이그레이션은 추가만 하고, 원격 DB에 reset하지 않는다.
**이유**: 대시보드 수작업 없이 Harness step 안에서 끝낸다.
**트레이드오프**: 사용자가 처음 한 번 Vercel 로그인과 Supabase 토큰 등록을 해야 한다. 실행기가 권한 확인 없이 명령을 실행하므로 금지 명령을 문서로 명확히 막아야 한다.

### ADR-012: 한국어만, 다크 테마 고정
**결정**: 화면은 한국어만 지원하고 문구는 `src/lib/messages.ts` 한 파일에 모은다. 다크 테마로 고정한다.
**이유**: 주 고객이 국내 교사·학생이다. 다크 테마는 강당·교실 TV에서 눈부심이 적고 상태 색이 잘 보인다. 테마·언어 전환 작업이 없다.
**트레이드오프**: 해외 사용자와 밝은 환경 선호 사용자를 당장 받지 못한다. 문구를 한 파일에 모아 두어 영어 추가는 쉽게 했다.

### ADR-013: 테스트는 순수 로직 단위 테스트 중심
**결정**: Vitest로 `lib`의 순수 함수(페이스, 이벤트 규칙, 결제 계산, 입력 검사)와 서버 액션·웹훅(외부 SDK는 목)을 테스트한다. DB 통합 테스트와 브라우저 E2E는 하지 않고, 실시간·결제·로그인은 손으로 확인하는 체크리스트로 검증한다.
**이유**: 작업 종료 훅이 매번 `npm test`를 실행하므로 외부 서비스·Docker 없이 빨리 끝나야 한다. 버그가 가장 많이 날 곳이 계산 로직이다.
**트레이드오프**: 실제 DB 동작과 기기 간 동기화는 자동으로 검증하지 못한다.
