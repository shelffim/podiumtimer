# Architecture Decision Records

## 철학
프로토타입 수준의 MVP다. 핵심 가치("구간마다 계획보다 빨랐는지 늦었는지"가 발표자의 페이스를 바꾸는가)를 검증하는 데 필요한 만큼만 만든다. 실서비스 수준의 견고함보다 작동하는 가장 단순한 구현을 고르고, 실서비스 전에 보강할 것은 PRD의 체크리스트로 미룬다. 외부 서비스는 Supabase, Polar, Vercel 세 개로 끝내고, 언어·접근 방식의 가짓수를 최소로 한다. 단, 돈과 권한에 관한 규칙(이용권 부여, 타이머·구간 한도, 비밀 키)은 프로토타입이어도 서버에서 지킨다.

---

### ADR-001: Next.js App Router + Vercel
**결정**: Next.js(App Router, TypeScript strict) + Tailwind CSS로 웹앱만 만들고 Vercel에 배포한다. 함수 리전은 서울.
**이유**: 발표자는 폰, 구간 설정은 노트북, 시청자는 링크로 들어온다. 설치 없이 세 경우를 모두 처리하는 건 웹이다. 화면·서버 액션·API 라우트를 한 저장소에서 처리하고, Harness의 TDD 가드와 훅이 Next.js 구조를 전제로 한다.
**트레이드오프**: 네이티브 앱의 진동(iPhone 브라우저는 미지원)과 백그라운드 실행을 포기한다. 앱 전환 시 페이지가 다시 열릴 수 있어서 localStorage 복원으로 대응한다. Vercel Hobby는 비상업 전용이라 실결제를 열 때 Pro로 바꿔야 한다.

### ADR-002: Supabase 하나로 인증·DB·실시간
**결정**: Supabase Auth(Google), Postgres, Realtime(Broadcast + Presence)을 쓴다. 프로젝트는 하나만 만든다.
**이유**: 서비스 하나로 로그인, 저장, 실시간 동기화, 접속자 표시를 해결한다. 무료 티어로 시작할 수 있고 서울 리전이 있다.
**트레이드오프**: Supabase에 종속된다. 무료 프로젝트는 1주 비활성 시 일시정지되고 Realtime 동시 연결이 약 200개다. 실서비스 전 Pro 전환이 필요하다.

### ADR-003: 발표자는 Google 로그인, 시청자는 닉네임만
**결정**: 발표자는 처음부터 Google로 로그인해야 앱을 쓴다. 시청자는 로그인 없이 닉네임만 입력한다.
**이유**: 타이머를 계정에 저장하면 노트북에서 만들고 폰에서 실행할 수 있다. 카카오는 앱 등록·동의항목 설정이, 이메일 로그인은 비밀번호 재설정 화면이 추가로 필요하다. 교실에서 학생이 링크만 열고 바로 들어오게 하려면 시청자 계정이 없어야 한다.
**트레이드오프**: 로그인 없이 써보는 체험이 없어서 첫 진입 장벽이 조금 높다.

### ADR-004: 판정은 구간별, ±1초는 정시
**결정**: 구간 차이(실제 − 계획)만 판정하고 누적 차이는 계산하지 않는다. 절댓값 1초 이하는 정시. 메인 숫자는 현재 구간 남은 시간이고, 타임라인 바는 진행 위치 하나만 보여준다.
**이유**: 이 앱의 목적은 어느 구간이 부족하고 넉넉한지 알려주는 것이다. 버튼을 누르는 반응 시간 정도는 오차로 본다. 진행 위치만으로도 전체 중 어디쯤인지는 보인다.
**트레이드오프**: "지금까지 전체로 몇 초 늦었나"는 바로 보이지 않는다. 대신 전체 남은 시간을 보여준다.

### ADR-005: 실행 상태는 발표자 기기에, 화면 값은 각자 계산
**결정**: 실행 상태에는 시작 시각, '다음'을 누른 시각들, `rev`만 두고 발표자 기기의 localStorage에 저장한다. [시작]할 때 구간을 함께 복사한다. 화면 값은 `computeTimer(구간, 실행 상태, 지금 시각)`으로 계산하고, 매초 상태를 보내지 않는다. 서버에는 완주한 기록과 공유 중인 상태만 저장한다.
**이유**: 일시정지·기기 간 조작이 없어서 서버 이벤트 기록·재전송 규칙·충돌 처리가 필요 없다. 연결이 끊겨도 시간이 계속 흐르고, 새로고침 후에도 정확히 이어진다. 구간 복사본 덕분에 진행 중 편집이 그 발표를 바꾸지 않는다.
**트레이드오프**: 발표 도중 다른 기기로 옮겨 이어갈 수 없다. 기기를 잃으면 진행 중이던 발표도 잃는다. 서버 시각 보정은 근사치라 수백 ms 오차가 날 수 있다(판정 허용치 1초보다 작음).

### ADR-006: DB 함수·트랜잭션 없이 supabase-js, 쓰기는 서버가 비밀 키로
**결정**: 로직은 전부 TypeScript에 두고 DB 접근은 supabase-js 하나로 한다. RPC, 트랜잭션, 직접 DB 연결은 쓰지 않는다. 쓰기는 서버가 사용자·소유권을 확인한 뒤 비밀 키로 하고, RLS는 자기 행 읽기만 허용한다. 동시성은 한 번의 조건부 업데이트(`shares.rev < 새 rev`)와 기본 키(`orders.id`, `shares.code`)로 막는다.
**이유**: 한 언어·한 접근 방식으로 끝나고, TDD 가드가 모든 로직에 적용된다. RLS가 쓰기를 허용하면 로그인한 사용자가 브라우저 세션으로 DB에 직접 써서 한도를 우회할 수 있다.
**트레이드오프**: 여러 쓰기를 원자적으로 묶지 못한다. 타이머를 동시에 만들어 무료 한도를 1개 넘는 드문 경우는 감수한다. 비밀 키는 RLS를 우회하므로 모든 서버 쓰기에 소유권 검사를 직접 넣어야 한다.

### ADR-007: 공개 Broadcast는 변경 힌트, 상태는 서버에서 다시 읽기
**결정**: 채널 `share:{code}`은 공개 채널이다. 발표자는 상태 저장이 성공하면 `changed {rev}`만 보내고, 시청자 화면은 이를 계기로 `/api/share/[code]`에서 상태를 다시 읽는다. 10초 주기와 화면 복귀 때도 다시 읽고, 조회는 한 번에 하나만 보낸다.
**이유**: 시청자 인증 없이도 누가 가짜 신호를 보내 화면을 조작할 수 없다. Broadcast가 실패하거나 신호를 놓쳐도, 발표자 연결이 잠깐 끊겨도 재조회로 복구된다. 비로그인 사용자에게 RLS 공개 정책을 열지 않는다.
**트레이드오프**: 신호마다 조회 요청이 생기고 10초 폴링이 있다 (링크당 최대 10명이라 부담이 작음). 저장 후 신호라 화면 반영이 저장 시간만큼 늦다.

### ADR-008: 공유는 발표 1회용 링크, 인원 한도는 화면에서 검사
**결정**: 공유 링크는 시작 전에만 만들고 발표 한 번 전용이다. QR, 링크 재발급, 개별 내보내기는 없다. [시작]할 때 구간과 인원 한도를 덮어쓴다. 동시 접속 한도는 Presence 인원 수로 화면에서 검사하고, 서버에서 강제하지 않는다.
**이유**: 링크 하나가 발표 하나라서 지난 발표 복구·채널 교체 처리가 필요 없다. 장난이 생겨도 그 발표가 끝나면 링크도 끝난다. 시작 때 덮어쓰면 링크를 만든 뒤 고친 구간과 결제한 플랜이 그 발표에 반영된다. 익명 계정·좌석 테이블·하트비트가 필요 없다.
**트레이드오프**: 진행 중에 장난치는 시청자를 막을 수 없다. 발표마다 링크를 새로 보내야 한다. 개발 도구로 Presence를 꾸며 한도를 우회하거나 다른 시청자를 밀어낼 수 있다(실결제 전 서버 강제).

### ADR-009: 결제는 Polar 30일권 하나 (USD, sandbox)
**결정**: 자동 갱신 없는 30일권($3.99) 하나만 판다. Polar를 판매 대행(Merchant of Record)으로 쓰고, MVP는 sandbox에서 전체 흐름까지 만든다. 다시 사면 만료일에 30일을 더한다.
**이유**: 토스페이먼츠 실결제는 사업자등록과 통신판매업 신고가 필요하다. Polar는 한국 거주 개인이 사업자 없이 정산받을 수 있고 세금 처리를 맡는다. 발표 타이머는 발표가 있을 때만 쓰는 도구라 구독보다 필요할 때 사는 이용권이 맞고, 갱신·해지·겹침 규칙이 필요 없다.
**트레이드오프**: USD로만 결제해서 원화 결제를 포기한다. 해외 결제가 되는 카드가 필요하다. 연간 구독 고객을 받지 못한다. Polar 수수료가 PG 직접 계약보다 높다.

### ADR-010: 만료일은 주문에서 계산, 환불은 수동
**결정**: 만료일 컬럼을 두지 않고 `orders`를 시간순으로 접어 계산한다(`만료 = max(만료, paid_at) + 30일`). 이용권은 서명 검증된 `order.paid` 웹훅에서만 생기고, 주문 ID 기본 키로 중복 웹훅을 무시한다. 환불은 Polar 대시보드에서 수동으로 하고 이용권은 회수하지 않는다.
**이유**: 계산식이 순수 함수 하나라 테스트가 쉽고, 같은 웹훅이 두 번 와도 기간이 두 번 늘지 않는다. 환불 웹훅·병합 규칙이 필요 없다.
**트레이드오프**: 환불해도 이용권이 자동으로 회수되지 않는다(실결제 전 `order.refunded` 처리).

### ADR-011: 무료 한도는 타이머·구간·동시 접속
**결정**: 무료는 타이머 3개, 구간 10개, 동시 접속 3명(발표자 포함). 30일권은 타이머 무제한, 구간 30개, 동시 접속 10명. 타이머·구간 한도는 새로 만들 때와 저장할 때만 서버에서 검사한다. 공유 링크 만들기는 제한하지 않는다.
**이유**: 이용권이 만료됐을 때 넘친 데이터를 잠그거나 지우는 처리가 필요 없다. 혼자 연습과 1:1 공유는 무료로 충분하고, 여러 명이 같이 보는 순간이 결제로 이어진다.
**트레이드오프**: 만료 직전에 타이머를 많이 만들어 두면 계속 쓸 수 있다(프로토타입이라 허용).

### ADR-012: mock/live 어댑터와 mock 선배포
**결정**: 화면은 `src/services/api`·`src/services/realtime` 인터페이스만 부르고, 구현은 mock(localStorage·BroadcastChannel·가짜 로그인·가짜 결제)과 live(서버 액션·Supabase·Polar) 두 개다. `NEXT_PUBLIC_DATA_MODE`로 고르고 기본값은 mock이다. mock 상태로 먼저 배포한다. 데이터 화면은 Client Component가 `services/api`로 읽는다.
**이유**: 외부 계정 없이 화면과 핵심 로직을 먼저 만들고 배포한다. 1차 배포로 운영 주소가 정해져야 Google 로그인과 Polar 웹훅을 설정할 수 있다. 컴포넌트 테스트도 mock 어댑터로 돌린다.
**트레이드오프**: 저장·전송 구현이 두 벌이다. mock 데이터가 브라우저에 있어서 Server Component에서 데이터를 읽는 패턴을 쓰지 않는다. mock에서는 서버의 조건부 업데이트·RLS·웹훅 동작을 확인할 수 없다.

### ADR-013: 환경은 하나, Vercel CLI·Supabase CLI로 배포와 DB 반영
**결정**: Supabase 프로젝트 1개, Polar sandbox만, 개발/운영을 나누지 않는다. `npm run deploy`(Vercel CLI)와 `npm run db:push`(Supabase CLI)로 배포와 마이그레이션 반영을 자동화하고, 두 명령은 해당 step에서만 실행한다. 마이그레이션은 추가만 하고, 원격 DB에 reset하지 않는다.
**이유**: 프로토타입에서 환경을 둘로 나누면 키·마이그레이션·웹훅 설정이 두 배가 된다. 대시보드 수작업 없이 Harness step 안에서 끝낸다.
**트레이드오프**: 로컬 개발과 배포가 같은 DB를 쓴다. 마이그레이션 실수가 바로 배포 환경에 반영된다. 사용자가 처음 한 번 Vercel 로그인을 해야 한다. 실행기가 권한 확인 없이 명령을 실행하므로 금지 명령을 문서로 명확히 막아야 한다.

### ADR-014: 한국어만, 다크 테마 고정, 폰 기준
**결정**: 화면은 한국어만 지원하고 문구는 `src/lib/messages.ts` 한 파일에 모은다. 다크 테마로 고정한다. 폰 360px을 기준으로 디자인한다.
**이유**: 주 고객이 국내 교사·학생이다. 다크 테마는 강당·교실에서 눈부심이 적고 의미 색이 잘 보인다. 발표자는 폰을 들고 조작한다. 테마·언어 전환 작업이 없다.
**트레이드오프**: 해외 사용자와 밝은 환경 선호 사용자를 당장 받지 못한다. 교실 TV·프로젝터 화면은 따로 맞추지 않는다. 문구를 한 파일에 모아 두어 영어 추가는 쉽게 했다.

### ADR-015: 테스트는 순수 로직 단위 테스트 중심
**결정**: Vitest로 `lib`의 순수 함수(실행 상태 규칙, 판정, 평균, 결제 계산, 입장 판정, 입력 검사)와 서버 액션·웹훅(외부 SDK는 목)을 테스트한다. DB 통합 테스트와 브라우저 E2E는 하지 않고, 실시간·결제·로그인은 손으로 확인하는 체크리스트로 검증한다.
**이유**: 작업 종료 훅이 매번 `npm test`를 실행하므로 외부 서비스·Docker 없이 빨리 끝나야 한다. 버그가 가장 많이 날 곳이 계산 로직이다.
**트레이드오프**: 실제 DB 동작과 기기 간 동기화는 자동으로 검증하지 못한다.

### ADR-016: 외부 디자인 시스템은 쓰지 않고 UI_GUIDE를 따른다
**결정**: 따로 만든 디자인 시스템(podiumtimer2: 흰 배경, 파랑 `#0052ff` 강조색, Inter·JetBrains Mono 웹폰트, 알약 버튼, 마케팅 페이지 구성)을 검토했고 토큰·컴포넌트·문구 규칙 모두 가져오지 않는다. 화면 규칙은 `docs/UI_GUIDE.md` 하나다. 이 검토에서 새로 정한 것은 서비스 이름 표기(`Podium Timer`, 로고 없이 시스템 글꼴의 흰 글자)뿐이다.
**이유**: 그 디자인 시스템은 제품 문서 없이 다른 브랜드의 마케팅 스펙을 옮겨 만든 것이라 이 앱의 결정과 부딪친다. 흰 배경은 다크 고정(ADR-014)과, 파랑 강조색은 "빠름" 파랑과, 초록 = 시간 남음은 "빠름에 초록 금지"와, 마케팅 랜딩은 MVP 제외 사항(랜딩 화면 미리보기)과 충돌한다. Inter에는 한글이 없어 바뀌는 건 숫자·영문뿐이다.
**트레이드오프**: 시간 숫자 모양이 기기마다 다르다(아이폰은 SF, 안드로이드는 Roboto 계열). 브랜드 색·로고 같은 시각적 정체성이 없다.
