# Architecture Decision Records

## 철학
MVP는 프로토타입이다. 동작하는 가장 단순한 구현을 고른다. 외부 서비스는 Supabase, Polar, Vercel 세 개로 끝낸다. 실서비스 수준의 견고함(서버 강제, 환경 분리, 모니터링)은 PRD의 "실서비스 전에 보강할 것"으로 미룬다. 단, 돈과 권한에 관한 규칙(이용권 부여, 타이머·구간 한도, 비밀 키)은 프로토타입이어도 서버에서 지킨다.

---

### ADR-001: Next.js App Router 웹앱, Vercel 배포
**결정**: Next.js(App Router) + TypeScript strict + Tailwind CSS로 웹앱만 만든다. Vercel 기본 주소(`*.vercel.app`)에 배포하고, 함수 리전은 서울.
**이유**: 발표자는 폰, 구간 설정은 노트북, 시청자는 링크로 들어온다. 설치 없이 세 경우를 모두 처리하는 건 웹이다. Server Action으로 별도 API 서버 없이 DB 쓰기를 서버에 둘 수 있다.
**트레이드오프**: 네이티브 앱의 진동(iPhone 브라우저는 미지원)과 백그라운드 실행을 포기한다. 앱 전환 시 페이지가 다시 열릴 수 있어서 localStorage 복원으로 대응한다.

### ADR-002: Supabase 하나로 로그인·DB·실시간
**결정**: Supabase Auth(Google), Postgres, Realtime(Broadcast·Presence)을 쓴다. 프로젝트는 하나만 만든다.
**이유**: 로그인, 저장, 실시간 공유, 접속자 표시가 서비스 하나로 해결된다. RLS로 "본인 행만" 규칙을 DB에서도 지킨다.
**트레이드오프**: Supabase에 종속된다. 무료 프로젝트는 1주 비활성 시 일시정지된다.

### ADR-003: 로그인 필수, Google 로그인만
**결정**: 앱을 쓰려면 처음부터 Google로 로그인해야 한다. 공유 시청자는 로그인하지 않고 닉네임만 입력한다.
**이유**: 타이머를 계정에 저장하면 노트북에서 만들고 폰에서 실행할 수 있다. 저장 경로가 하나라 단순하다. 카카오는 앱 등록·동의항목 설정이, 이메일 로그인은 비밀번호 재설정 화면이 추가로 필요하다.
**트레이드오프**: 로그인 없이 써보는 체험이 없어서 첫 진입 장벽이 조금 높다.

### ADR-004: 결제는 Polar(USD), 토스페이먼츠 아님
**결정**: Polar를 Merchant of Record로 쓰고 sandbox에서만 결제한다. 가격은 $3.99.
**이유**: 토스페이먼츠 실결제는 사업자등록과 통신판매업 신고가 필요하다. Polar는 한국 거주 개인이 사업자 없이 개인 계좌로 정산받을 수 있고, 세금 처리를 대신한다.
**트레이드오프**: Polar는 USD로만 결제하므로 원화 결제를 포기한다. 사용자는 해외 결제가 되는 카드가 필요하고 해외 결제 수수료가 붙을 수 있다.

### ADR-005: 30일권 1회 결제, 만료일은 주문에서 계산
**결정**: 자동 연장 없는 30일권. 만료일 컬럼을 두지 않고 `orders`를 시간순으로 접어 계산한다(`만료 = max(만료, paid_at) + 30일`). 이용권 부여는 서명 검증된 `order.paid` webhook에서만 하고, order id를 기본 키로 해서 중복 webhook을 무시한다.
**이유**: 발표 타이머는 발표가 있을 때만 쓰는 도구라 월 구독이 어색하다. 구독 갱신·해지·실패 처리가 필요 없다. 계산식이 순수 함수라 테스트가 쉽고, 같은 webhook이 두 번 와도 기간이 두 번 늘지 않는다.
**트레이드오프**: 환불해도 이용권이 자동으로 회수되지 않는다(실서비스 전 보강).

### ADR-006: 무료 한도는 타이머·구간·동시 접속
**결정**: 무료는 타이머 3개, 구간 10개, 공유 동시 접속 3명(발표자 포함). 30일권은 타이머 무제한, 구간 30개, 동시 접속 10명. 타이머·구간 한도는 새로 만들기와 구간 추가 때만 서버에서 확인한다. 동시 접속 한도는 링크를 만들 때의 이용권으로 정하고, 시청자 화면이 Presence 인원 수로 확인한다.
**이유**: 이용권이 만료됐을 때 넘친 데이터를 잠그거나 지우는 처리가 필요 없다. 혼자 연습·1:1 공유는 무료로 충분하고, 여러 명이 같이 보는 순간이 결제로 이어진다. Presence로 세면 좌석 테이블·하트비트가 필요 없다.
**트레이드오프**: 만료 직전에 타이머를 많이 만들어 두면 계속 쓸 수 있다. 동시 접속 한도는 개발 도구로 우회할 수 있다(실서비스 전 서버 강제).

### ADR-007: 판정은 구간별, ±1초는 정시
**결정**: 구간 차이(실제 − 계획)만 판정하고 누적 차이는 계산하지 않는다. 절댓값 1초 이하는 정시. 타임라인 바는 진행 위치 하나만 보여주고 계획 대비 위치는 표시하지 않는다.
**이유**: 이 앱의 목적은 어느 구간이 부족하고 넉넉한지 알려주는 것이다. 버튼을 누르는 반응 시간 정도는 오차로 본다. 진행 위치만으로도 전체 중 어디쯤인지는 보인다.
**트레이드오프**: "지금까지 전체로 몇 초 늦었나"는 바로 보이지 않는다. 대신 전체 남은 시간을 보여준다.

### ADR-008: 시간은 타임스탬프로 저장하고 각 기기가 계산
**결정**: RunState에는 시작 시각과 "다음"을 누른 시각만 저장한다. 화면 값은 각 기기가 `서버 보정 시각`으로 매번 계산한다. 서버 보정은 `/api/time` 한 번 호출로 구한 offset을 쓴다. 실행 상태는 발표자 기기의 localStorage에 두고, 완주한 발표만 서버에 기록한다.
**이유**: 연결이 끊겨도 시청자 화면의 시간이 계속 흐르고, 새로고침 후에도 정확히 이어진다. 기기마다 시계가 달라도 같은 값을 보여준다. 일시정지·기기 간 조작이 없어서 서버 이벤트 기록·충돌 처리가 필요 없다.
**트레이드오프**: 보정은 왕복 시간의 절반을 더하는 근사치라 수백 ms 오차가 날 수 있다. 판정 허용치(1초)보다 작아서 허용한다. 발표 도중 다른 기기로 옮겨 이어갈 수 없다.

### ADR-009: 공유는 발표 1회용 링크 + 닉네임 입장
**결정**: 링크는 시작 전에만 만들고 발표 한 번 전용이다. 시청자는 로그인 없이 닉네임만 입력한다. QR, 링크 재발급, 개별 내보내기는 없다. 구간은 "시작" 때 발표자가 쓰는 구간으로 덮어쓴다.
**이유**: 링크 하나가 발표 하나라서 지난 발표 복구·채널 교체 같은 처리가 필요 없다. 장난이 생겨도 그 발표가 끝나면 링크도 끝난다. 시작 때 덮어쓰면 링크를 만든 뒤 타이머를 고쳐도 발표자와 시청자가 어긋나지 않는다.
**트레이드오프**: 진행 중에 장난치는 시청자를 막을 수단이 없다. 발표마다 링크를 새로 보내야 한다.

### ADR-010: Broadcast는 변경 신호, 상태는 서버에서 다시 읽기
**결정**: 발표자는 상태를 `shares.state`에 저장한 뒤 공개 채널로 `changed` 신호만 보낸다. 시청자는 신호를 받거나 10초마다, 화면 복귀·재연결 때 `/api/share/[code]`로 다시 읽는다. 이 경로만 admin 클라이언트로 그 코드의 행 하나를 읽는다.
**이유**: 공개 채널이라도 가짜 메시지로 시청자 화면을 바꿀 수 없다. 신호를 놓치거나 발표자 연결이 잠깐 끊겨도 재조회로 복구된다. 비로그인 사용자에게 RLS 공개 정책을 열지 않는다.
**트레이드오프**: 조회 경로 하나와 10초 폴링이 생긴다(링크당 최대 10명이라 부담이 작음). 저장 후 신호라 화면 반영이 저장 시간만큼 늦다.

### ADR-011: mock/live 구현과 mock 선배포
**결정**: 화면은 `src/services/api`·`src/services/realtime` 인터페이스만 부르고, 구현은 mock(localStorage·BroadcastChannel·가짜 로그인·가짜 결제)과 live(Server Action·Supabase·Polar) 두 벌이다. `NEXT_PUBLIC_DATA_MODE`로 고르고 기본값은 mock이다. 데이터 화면은 Client Component가 `services/api`로 읽는다.
**이유**: 외부 계정 없이 화면과 핵심 로직을 먼저 만들고 배포한다. 1차 배포로 운영 주소가 정해져야 Google 로그인과 Polar webhook을 설정할 수 있다. 컴포넌트 테스트도 mock 구현으로 돌린다.
**트레이드오프**: 저장·전송 구현이 두 벌이다. mock 데이터가 브라우저에 있어서 Server Component에서 데이터를 읽는 패턴을 쓰지 않는다. mock에서는 webhook·RLS 동작을 확인할 수 없다.

### ADR-012: 환경은 하나, 배포는 CLI
**결정**: Supabase 프로젝트 1개, Polar sandbox만, 개발/운영을 나누지 않는다. 배포는 `npm run deploy`(Vercel CLI), 마이그레이션은 `npm run db:push`(Supabase CLI, `DATABASE_URL`)로 해당 step에서만 실행한다. 마이그레이션은 추가만 하고 원격 DB를 reset하지 않는다.
**이유**: 프로토타입에서 환경을 둘로 나누면 키·마이그레이션·webhook 설정이 두 배가 된다. 대시보드 수작업 없이 Harness step 안에서 배포와 DB 반영을 끝낸다.
**트레이드오프**: 로컬 개발과 배포가 같은 DB를 쓴다. 마이그레이션 실수가 바로 배포 환경에 반영된다. 사용자가 처음 한 번 Vercel 로그인을 해야 한다.
